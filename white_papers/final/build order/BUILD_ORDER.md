# Build Order — corrected

Supersedes the previous `BUILD Order cf8a8428393d.md` + `Flat Table Database 2766ea9dcf5c.csv`.

**Why the previous version was replaced:** that tree described a **single-core RISC-V SoC**
(`rv32i_subsystem`, `imem_sram`, `dmem_sram`, `cpu_ctrl_reg`, `perf_counters`,
`user_project_wrapper`). It is not this project, and it contradicts three closed decisions:

1. **The WP puts the processor core out of scope** — §1.4, "Out of scope: Processor core RTL
   (stimulus via testbench)". The committed 2×2 budget (≈13,000–19,000 LUTs, 28 BRAM36) is the
   **coherence fabric only** — router + L1 + L2 bank + directory + NIC + tap. Instantiating an
   RV32I core, an imem and a dmem **per tile** is 4× that budget and breaks both the LUT ceiling
   (53,200) and the BRAM target.
2. **It omitted three modules the design cannot be built without** — `mem_tap` (§3.9), `cpu_tile`
   (§3.1 integration) and `mesh_top` (the N×N instantiation with the TILE_ID and corner-port
   tie-offs), plus the **JTAG stimulus source** (§6.1 / §16.14, the FPGA validation stimulus).
3. **It placed the DMA tile at build order 85 with no gate marker.** Ruling **B4** withdrew DMA
   from the 2×2 build entirely: the committed 2×2 mesh has exactly four tile positions, all CPU
   tiles, and §3.11's DMA tile is the 16th tile of a 4×4 mesh. The DMA tile is **gated on the
   Week-8 gate exit and is 4×4-simulation-only**.

**Ordering correction vs the previous plan:** the **L2 bank and its controller move ahead of the
directory controller**. The directory side *writes the bank* (its fill path, the `DIR_E + PUTM`
write-back, the dirty-bit set/clear), so it cannot be written against an undefined bank
interface. Either build the bank first or freeze the bank port as an explicit stub — but do not
leave it implicit.

**Scope correction:** the directory and the L2 bank are per-**CPU tile** (the 2×2 build has four
banks, the 4×4 has sixteen), so `l2_bank`, `l2_ctrl` and `dir_ctrl` are instantiated **inside
`cpu_tile`**, not once per mesh.

## Green criterion per module (four items, not three)

A module is green only when **all four** hold:

1. **RTL unit green** — compiles, passes its unit tests.
2. **SVA category clean** — BMC K = 64 for the assertion categories that gate the module.
3. **Reference-model shadow agrees** — the scoreboard shows zero mismatches on the module's
   directed tests (F1–F9 for the L1/directory slice, WP §5.1 tests 1–17 for the fabric).
4. **Package gate still green** — `python3 verify_patch_set.py --dir . --build-script
   build_diagrams_html.py` reports 130/130, exit 0. The reference model and the SVA set move in
   lockstep with the spec, so any spec edit in the RTL phase must re-run the gate.

**§16.1 and §16.2 land together.** The exclusive bit is generated by the directory (rule 9) and
consumed by the L1; F8 is only meaningful when both sides exist, and A1.2 ("at most one L1 in E")
is the assertion that catches a wrongly generated bit.
